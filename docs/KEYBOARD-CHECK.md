# キーボードで学習操作を確認する（#4）

english.dashcloudly.com・kobun.dashcloudly.comに関する学習UIの確認手順です。**この公開用リポジトリの生成デモだけ**を使います。両本番サイト、教材入りの作業コピー、実アカウントには接続しません。デモの確認結果を、そのまま英語版・古文版の本番での動作保証にはしないでください。

このガイドのフォーカスは「期待値」です。現状で必ず満たすという意味ではありません。不一致は別Issueに記録し、この課題では実装を修正しません。

## 1. 準備

Node.js 22以降で、この公開用リポジトリを新しいフォルダへcloneして起動します。既存環境の設定や学習記録を削除してデモ化しないでください。

```sh
git clone https://github.com/rattokun-1/dashcloudly-learning-web.git
cd dashcloudly-learning-web
npm start
```

1. 新しいブラウザープロファイル、またはシークレット／プライベートウィンドウを使います。ブラウザー本体の全データは消しません。
2. `shared/config.local.json`が存在しない新規cloneを使います。`npm run configure`、Local／Connectedへの変更、教材ファイルのコピーは行いません。
3. `http://localhost:3000/apps/study/`を開きます。画面の「UIデモ · 教材データなし」と、生成された「項目001」「説明 001」のような表示を確認します。実際の単語・訳・利用者名が表示されたら中止します。
4. 初回案内があれば、Tabで「同意する」へ移動してEnter、アカウント設定は「後で設定する」を選び、案内の「次へ」「学習を始める」をEnterで進めます。ログインや外部のリンクは開きません。
5. 初期の6択形式、出題対象「すべて」を使います。正誤や出題順は判定条件にしません。英語版の語・訳、古文版の語・現代語訳の代わりに、同じ生成項目で共通操作を確認します。

## 2. ブラウザー・画面幅

各ブラウザーの正確なバージョンとOSを記録します。「最新版」だけでは記録しません。画面幅は外側のウィンドウ幅ではなく、**ビューポートのCSS px（幅×高さ）**です。ズーム100%、拡張機能なしで開始します。幅を狭くしたデスクトップブラウザーの確認は、実スマートフォンや外付けキーボードの確認とは区別します。

| ブラウザー | 確認するビューポート | 実施時の記録 |
| --- | --- | --- |
| Chrome（Windows） | 1440×900、390×844 | バージョン、OS、各手順の結果 |
| Edge（Windows） | 1440×900、390×844 | バージョン、OS、各手順の結果 |
| Firefox（WindowsまたはmacOS） | 1440×900、390×844 | バージョン、OS、各手順の結果 |
| Safari（macOS） | 1440×900、390×844 | バージョン、OS、Tabで全コントロールへ移動する設定の有無 |

追加で768×1024（タブレット相当）・320×740（狭幅）も確認できます。DevToolsで幅を設定する場合は、**開始前にDevToolsを閉じ、Webページに戻ってから**試します。Safariでは「Tabキーを押したときにWebページ上の各項目を強調表示」など、使用バージョンのキーボードナビゲーション設定を有効にします。ブラウザーやOSのキー設定を変えた場合も記録してください。

## 3. Tab・Enter・Escapeだけで確認する

環境設定後はマウスでボタンを押したり、Consoleから`.focus()`や学習関数を実行したりしません。Tabの回数は幅やブラウザーで変わるため固定しません。フォーカス枠とラベルを見て移動します。画面外へ行った場合は、自動でスクロールして対象が見えることも確認します。

| 手順 | キー操作 | 期待する画面・動作 | 期待するフォーカス |
| --- | --- | --- | --- |
| K1 学習開始へ移動 | Tabを繰り返す | 「クイズ開始」を含む開始ボタン（表示名が変わっている場合は学習開始のボタン）へ到達できる。隠れた画面へ移動しない | `#btn-start-quiz`に視認できる枠 |
| K2 学習開始 | 開始ボタンでEnterを1回 | 第1問が表示される。1回の押下で複数問進まない | 表示中の第1選択肢。開始ボタンやBODY、隠れた画面に残らない |
| K3 選択肢を選ぶ | Tabで任意の選択肢へ移動しEnterを1回 | 選んだ答えの正誤と解答を表示。まだ次の問題へ進まない | 回答後の「次の問題へ」ボタン（`#next-btn`）。無効化した選択肢に残らない |
| K4 次の問題 | 「次の問題へ」でEnterを1回 | 問題番号が1つだけ増え、新しい選択肢が表示される | 新しい第1選択肢。非表示になった`#next-btn`やBODYに残らない |
| K5 未回答で中断を開く | Tabで「中断」へ移動しEnter | ブラウザーの中断確認ダイアログを1つ表示。問題番号は増えない | ダイアログ内のボタンに操作対象が移り、背後の学習画面は操作されない |
| K6 中断を取り消す | 確認ダイアログでEscape | ダイアログだけ閉じる。同じ問題・同じ回答状態のまま学習を続けられる | 押した「中断」ボタンに戻り、枠が見える |
| K7 回答後にも中断を開く | 同じ問題の選択肢をTab・Enterで回答し、Tabで「中断」へ移動してEnter | 「次の問題へ」が表示中でも中断確認を開く。問題番号は増えない | 中断確認ダイアログ内。Enterが別ボタンの操作に置き換わらない |
| K8 中断を確定する | ダイアログ内でTabにより「OK」等の肯定ボタンを選びEnter | 学習を中断して範囲選択画面へ戻る。結果や次の問題を勝手に表示しない | 戻り先の開始ボタン（`#btn-start-quiz`） |
| K9 再度開始する | 戻り先でEnter | 同じ操作経路で再開でき、フォーカスを見失わない | 表示中の第1選択肢 |

「中断」が複数表示される幅では、各ボタンをそれぞれ試します。K7で確認画面が開かなければその時点で失敗として記録し、K8を成功扱いにしません。K8は未回答の状態からK5をやり直して、独立して確認できます。

Escapeはこの手順では**ブラウザーの中断確認を取り消すキー**です。学習画面でEscapeだけを押して中断できるとは扱いません。確認画面の文言・最初に選ばれるボタン・Tab順はブラウザーにより異なるため、肯定ボタンを確認してからEnterを押します。確認画面内で別の問題へ進む場合は不具合です。

## 4. 結果を記録する

各K番号に「合格／不合格／未確認」を付けます。途中で失敗して続行できない場合、後続を合格にせず、どの前提が満たせなかったか書きます。

```text
確認日：YYYY-MM-DD
対象：英語版関連／古文版関連の共通生成デモ（本番未確認）
コミット：git rev-parse HEAD の結果
ブラウザー／バージョン：
OS：
ビューポート：幅×高さ CSS px、ズーム100%
設定：Tabナビゲーション、拡張機能、手動／自動の別
使用データ：demoContent()の生成項目のみ、未ログイン
結果：K1=、K2=、K3=、K4=、K5=、K6=、K7=、K8=、K9=
実際にフォーカスした要素：ラベル、IDまたはBODY、枠の有無
別Issue：URL、または未起票の再現手順への参照
```

2026-10-18時点のローカル確認では、Windows（OS build 10.0.26300.0）・Chrome 155.0.8059.85のヘッドレスブラウザー、1440×900と390×844でK2〜K4のフォーカス不一致を確認しました。K7のEnter競合は1440×900でも再現しています。Tab・EnterはブラウザーのキーボードAPIで送りました。ネイティブ確認画面はAPIで取り消しているため、**K6の実キーEscapeとK8の実キーによる確定は手動確認が残っています**。Edge・Firefox・Safari・実機での確認も未実施です。

2026-10-20にPR #9マージ後の`5b49303`でも再確認しました。Chrome 155.0.8059.85、1440×900・390×900で、画面更新後に2フレーム待ってから読むとK2〜K4はいずれもBODYへフォーカスが移りました。390×900ではK7も再現し、確認ダイアログなしで問題番号が1つ増えました。1440×900のK7は今回の確認で結果が一定ではないため、10月18日の結果と区別し、成功扱いにはしません。初回案内完了を端末内のテスト設定で準備した後、Tab・Enterで操作し、`.focus()`や学習関数の直接実行はしていません。実キーEscapeでのネイティブ確認取消・確定と他ブラウザーの確認は引き続き未確認です。

## 5. 問題は別Issueへ

1件につき1つの不具合として、[不具合報告フォーム](https://github.com/rattokun-1/dashcloudly-learning-web/issues/new?template=bug_report.yml)へ整理し、関連課題に`#4`を書きます。原因の推測よりも、開始状態・押したキーの順序・期待フォーカス・実際のフォーカス・再現頻度を優先します。

確認できた問題は、別Issueとして起票し、確認範囲と再現手順を分けています。ローカルの記録も残しています。

- [学習の画面遷移でフォーカスを失う（#10）](https://github.com/rattokun-1/dashcloudly-learning-web/issues/10) · [確認記録](issue-drafts/keyboard-focus-loss.md)
- [回答後に「中断」でEnterを押すと次の問題へ進む（#11）](https://github.com/rattokun-1/dashcloudly-learning-web/issues/11) · [確認記録](issue-drafts/keyboard-interrupt-enter.md)

添付なしのテキストだけで再現できる形を基本にします。実教材、実単語・訳の一覧、プロフィール、メール、回答履歴、学校情報、認証情報、設定ファイル、Cookie、HAR、localStorageの書き出しは添付しません。画像が必要な場合も新規の生成デモだけにし、アドレスバー、別タブ、通知、アカウント表示に個人情報がないことを目視確認します。[公開ポリシー](PUBLICATION.md)も参照してください。
